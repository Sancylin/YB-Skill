# 通用装配与视觉角色

以下布局/视觉模式仅在现场团队规范可追溯且场景命中时作为 team-rule；无依据时为可解释调整的 heuristic，不以本文措辞独立阻断。工具限制、实例身份保护和需求覆盖仍为硬性不变量。规则分类见 [采集与验证契约](capture-and-validation.md)。
本文件是全局装配协议，适用于所有页面、容器、业务组合、自建组件与内容槽，不按组件名称触发。具体组件约束与 token 从现场读取；正式实例内部只读核验，修改遵守写入白名单。

## 1. 节点角色

- `viewport`：页面或设备的可见边界与页面背景。
- `layout-only`：排列、间距、对齐、滚动和响应式关系；无独立视觉。
- `surface`：有明确可见背景、边界或层级的功能区域。
- `content`：文字、图像、媒体或数据。
- `separator`：分隔内容组。
- `overlay`：与主流分层的模态或非模态内容。
- `documentation`：画布说明，不属于产品。

创建或修改容器前，分别判断布局职责（怎样排列子节点）和视觉职责（是否独立承载内容或表达层级）。Auto Layout 是布局机制，不意味着需要背景；有背景也不意味着不用 Auto Layout。角色依据职责而非名称、组件类型或嵌套深度。角色不明确就不加填色、投影或裁切。

## 2. 尺寸与布局

- 设备类别和画布尺寸来自 PRD、目标文件或现场正式模板。
- 屏幕规格（`Screen Spec`）为每个槽位写固定、自适应、填充、居中、滚动和适配策略。
- 复用现网已有屏幕/模式时，尺寸、间距、圆角等数字来自 `liveBaseline` 的现场几何；逐元素对照 `live/ours/delta`，超出容差要修或写明授权偏差，不能凭印象新造。
- 正式组件保持现场默认尺寸约束；是否通栏、居中或可拉伸按其 description。
- 结构关系使用 auto-layout Frame；绝对定位只用于明确 overlay。
- 不把某次项目的宽高、边距或组件尺寸升级为全局常量。

## 2.1 布局宿主

产品结构必须是 auto-layout Frame：viewport 内的内容柱、模块列、浮层内容槽、自建缺口。禁止用 Group 当页面或模块根。

编组只允许选中后瞬间搬家，随即放进 auto-layout 父级并拆组。因字体或其他插件限制无法 `appendChild` 进 Frame 时，记 layout `degraded` 并写人工接管；不得把 Group 当交付结构。

## 2.2 对齐与分布：每个布局宿主都要判断

先确定内容顺序与方向，再分别选择水平 left / center / right、垂直 top / center / bottom。依据阅读起点、成组关系、等权内容的重心、前后端锚定及固定边界判断；左上可以正确，但不能省略判断而继承默认，也不能为了用遍九种对齐强行居中。跨语言按阅读方向解释起止端。

选型前在 Screen Spec 记录方向、水平/垂直对齐目标及理由、紧凑排列或两端分布、子节点宽高策略。选型后映射为实际工具属性。Figma 非换行紧凑排列时，下表单元格均为 `(primaryAxisAlignItems, counterAxisAlignItems)`：

| 对齐目标 | HORIZONTAL 横排 | VERTICAL 竖排 |
|---|---|---|
| 左上 | MIN, MIN | MIN, MIN |
| 上中 | CENTER, MIN | MIN, CENTER |
| 右上 | MAX, MIN | MIN, MAX |
| 左中 | MIN, CENTER | CENTER, MIN |
| 正中 | CENTER, CENTER | CENTER, CENTER |
| 右中 | MAX, CENTER | CENTER, MAX |
| 左下 | MIN, MAX | MAX, MIN |
| 下中 | CENTER, MAX | MAX, CENTER |
| 右下 | MAX, MAX | MAX, MAX |

九宫格不是全部布局能力，以下决策分别处理：

- **尺寸与剩余空间**：对齐在扣除 padding 后的内容框内生效。父轴 Hug 或子节点 Fill 占满时可能没有剩余空间，不能靠 CENTER / MAX 获得预期位置。需要锚定或居中时，先确定由谁提供有界空间；不要为了显出对齐效果凭空放大容器。页面级空/错/弱网缺省的有界空间是**整机画板**，不是扣除顶栏后的剩余列；顶栏叠在缺省层之上，不把居中参考框的上边界改到顶栏下沿。
- **紧凑与两端分布**：紧凑组使用声明 gap；只有需要将首尾锚定两端、且存在可分配空间时才用主轴 `SPACE_BETWEEN`。它不是九宫格的一格，不等于等宽，也不等于固定间距；子节点 Fill、数量变化、单子节点情况必须验证。
- **混合对齐**：父级控制一组子节点，不代表所有后代都同样对齐。不同子组需要不同锚点时，用有职责的透明嵌套布局实现，保留阅读顺序；不用空白文字、装饰性占位块或手调 x/y 模拟对齐。
- **文字**：Text 在父级的位置、文本框内的 `textAlignHorizontal` / `textAlignVertical`、同排文字的基线是三件事，分别判断。不能为了容器居中把长正文也设成居中；不同字号需要基线对齐时，横排交叉轴可用 `BASELINE`，竖排不能照搬。
- **换行**：WRAP 分别判断行内对齐与多行分布；记录每行间距、可用宽度及最后一行行为，不把单行九宫格机械套在多行容器上。工具支持的方向和属性先查能力。
- **正式实例**：外部宿主决定实例位置，实例内部服从现场规范；不通过改正式后代对齐、拉伸或文字样式修复外层错误。

创建时显式设置自建宿主的方向、主/交叉轴对齐与宽高策略；先建立合法父子关系再设置 Fill/Hug。修改文案、子项数量、方向、尺寸、变体或宿主后重新检查，不能只检查首次创建。

验收同时读回布局属性和最终几何：在正常阅读尺度检查相对内容框的位置、基线、边界与间距；验证短/典型/长内容以及范围内窄/宽尺寸。截图恰巧对齐不能替代结构证据，参数正确也不能替代视觉证据。

## 3. 裁切（`clip`）判断

逐层判断：

1. 节点是否定义可见边界或必须隐藏越界内容？是则裁切。
2. 节点是否依赖裁切形成图像或几何形状？是则裁切。
3. 节点或后代是否需要越界绘制投影、提示或浮层？相关中间容器不得裁掉它。
4. 纯 layout-only 且没有边界职责时，默认不裁切。

外层 viewport 裁切与内层 surface 不裁投影可以同时成立。验收必须同时检查“内容泄出最终边界”和“中间层误裁视觉效果”。

检查方式不能只靠肉眼看截图：Figma 读回节点 bbox，与最近的 `overflow:hidden` 祖先或视口比较；Demo 断言 `getBoundingClientRect` 与 `scrollWidth/scrollHeight`。发现逃逸先修，再留 overflow 证据。

## 4. 视觉职责与透明容器

- 只有排列、对齐、间距、尺寸分配或滚动职责的容器判为 layout-only，不承担可见表面。新建时显式设置 `fills = []`、`strokes = []`、`effects = []`；不依赖工具默认，不用白色或零透明度色块代替无填充。
- 有独立内容分组、交互边界或空间层级职责的区域才可判为 surface / overlay；装饰和分隔也需明确语义依据。不是每个 Frame 都需要视觉边界，也不是每个独立区域都必须涂底。
- viewport 承担页面背景；内容自身的文字色、图像、状态表达不能被误当成布局污染。
- 创建、迁入、重新包装或批量改样式后读回视觉属性。清空规则只作用于本次自建且已判为 layout-only 的节点，禁止遍历所有 Frame 清空背景或改正式实例内部。
- 主题使用现场变量和 mode；主背景、次级背景、弱分割、浮起效果是语义选择，精确 token 身份和值从现场解析，不按名称猜绑定。

## 4.1 所有层级的表面区分

先确定页面背景，再从外向内判断每个独立表面和同层兄弟的关系。既检查父子融合，也检查并列区域是否混淆；穿过透明祖先找到最近实际可见背景，结合主题解析值、透明度、媒体、蒙层和已有边界。不同 token 名不保证区分，同色也不自动构成缺陷。

Screen Spec 保留 `canvasRole`：`primary` 表示连续主内容或有固定主场景背景职责；`grouped` 表示整页以重复独立内容组为主、需要背景承载分组。按整体任务与规范选，不由某个子件、导航深度或组件名称决定；展示台配色不能反推产品背景。

对需要区分但实际区分不足的区域，选择一种足够且符合层级的主要方式：

| 判断依据 | 优先方式 | 约束 |
|---|---|---|
| 已有边界、留白或层级线索足够表达职责 | 保持现状 | 不为了同色或套用规则增加装饰 |
| 父背景有稳定职责，子区域需要独立分组且允许换底 | 局部表面使用相邻层级的正式背景 token，通常考虑 secondary 语义 | 保留父背景；不能把整条内容流一起着色，也不机械逐层交替底色 |
| 子区域需要保留原背景，以边界表达分组 | 使用正式弱分割描边，现场可对应 divider soft | 确认组件允许并实际可见，不把描边当通用默认 |
| 区域相对承载面确有浮起、覆盖或空间高度职责 | 沿用正式投影/浮起效果 | 不能仅为增加对比制造虚假高度；检查效果是否被裁切 |
| 整个页面本就以独立内容组为主，兄弟区域有一致承载需求 | 使用 grouped 页面背景，保留子表面的合规背景 | 属于整页决策，不为单个局部问题任意换底 |

投影、描边、背景变化可有规范规定的组合，但不能作为修复步骤逐个叠加。正常阅读尺度下，依赖边界识别的分组或交互仍不清楚时，必须记录并修复；反之，不强制给可由留白清楚表达的内容新增表面。

## 4.2 递归应用与实现权限

- 上述判断应用到任意嵌套层，不只检查页面第一层或某类组件。父级有背景不代表所有后代都透明：独立子表面可以有视觉，纯布局后代必须透明；每增加一层视觉都要有新增职责。
- 自建表面按职责绑定现场 token；正式实例优先使用公开 Variant、属性或合法组合。允许的实例级覆盖必须有 description 依据并列入白名单。除现场 description 明确要求的间距示意填充（只改填充可见性，不删层）外，不直接改后代视觉、不解绑 token、不 detach、不修改规范源。description 要求去掉示意填充时必须执行，不能把库默认示意色直接交付。
- 正式件无法合法满足层级需求时，重新检索候选或组合；仍无解则记录规范与场景冲突及恢复入口。不能伪造 gap 重画已有资产，不能擅改父背景规避问题，也不能因“组件默认如此”免除可见缺陷。
- 角色、对齐和区分理由写入 Screen Spec；选型后在实现日志补节点、合法属性及基础规范证据。统一规则适用于 Figma 与原型装配，不把某次产品配方写回 Skill。

颜色、分割与效果通过 [foundations/index.md](foundations/index.md) 现场读取。

## 4.3 浮层高度

浮层默认随内容 hug。手册里的分档高度或最大高度，只有现场 description **和** 当前场景同时要求时才用。禁止从其它项目抄高度。

## 5. 间距

先读相邻正式件 description，再决定外层要不要加距：

- **声明距**：description 写了对外间距，或写了内部间距示意层（保留几何、按 description 处理填充）。只使用该声明距；外层同方向不再加 gap 或 padding。示意填充不得留在交付可见态。
- **补距**：自建缺口，以及 description 没有对外间距声明的正式件（放在内容流之外，或与未声明距的组件拼在一起）。外层 layout-only 按 [foundations/index.md](foundations/index.md) 打开 `✅ 间距 Spacing` 和 `间距规范`，用变量绑 padding、itemSpacing 和页面边距。
- 父级不得重复叠加已经由子组件声明的外部间距。
- 禁止用绝对坐标代替 auto-layout 间距。
- 行内原子、纵向块、滚动模块和 overlay 分别按其职责确定间距宿主，不把一种容器规则套到所有场景。
- **圆角组旁的标题/说明**：标题 + 圆角表单/列表组，或圆角表单底部的辅助说明，仍左对齐；但文字不要贴圆角外框。水平内边距让文字光学边缘对上容器**内边内容**（与组内第一列文字大致齐），避免外框切角把说明显得更靠外。间距从现场相邻正式件或间距规范读，不把某次数值写成全局常量。对话里的 Markdown 正文流不套这条。

## 5.1 贴边壳层 vs 内容内收

同一屏里，先把每个横向区域判成两类，再决定谁吃页面边距。命中时同时应用 [interaction-patterns.md](interaction-patterns.md) 的 `edge-chrome-vs-content-inset`。

| 角色 | 判断 | 宽度 | 页面边距落在哪 |
|---|---|---|---|
| **贴边壳层** | 替换或延续设备顶/底边缘的操作面：导航栏、长按条、锁定后的取消/麦/发送条、系统键盘、Tab、全宽底栏。有独立表面，贴着画布左右缘，不能从两侧看见页面背景或蒙层缝。 | 铺满当前设备画布（或 iPad 模板给出的整机宽度），`FILL` 画布，父级左右 padding = 0 | **不落在这层，也不落在同时包含着它的父级上**。条内图标/文案的左右留白是组件内部距，不是页面边距。系统键盘用正式系统输入法示意件，规则见 `system-ime-keyboard` |
| **内容内收** | 停在壳层之上或内容柱里的卡片、流式文本框、列表、表单组。需要离开屏幕左右缘，避免文字和圆角贴边。 | 在画布宽度上扣除页面边距；用内容自己的 inset 包装，或 Hug/Fixed 后在无左右 padding 的父级里居中 | 只包这层。边距数值从 `✅ 间距 Spacing` / `间距规范` 读，不写进 Skill |

禁止：把页面左右 padding 加在「文本框 + 贴边底栏」的同一个父级上——底栏会被一起内收，两侧露出背景。正确拆分：父级铺满、无左右 padding；文本框单独 inset；底栏/键盘 `FILL`。

验收：对照截图看底栏左右是否与画布（或同屏长按绿条、顶栏）齐平；能看见蒙层或页面背景从底栏两侧漏出，就是把内容边距套到了壳层上。

## 6. 自建层

- 业务 layout-only 与一次性内容按角色创建；可复用交互能力仅在现场证明真实 gap 后组件化。
- 颜色、文字、圆角、投影、蒙层、分割、间距和 iPad 适配均通过 [foundations/index.md](foundations/index.md) 指向的现场页解析。
- 自建层与相邻正式件保持同一密度、层级和适配策略。
- 不仿制已有正式资产的外壳或内部件。

## 7. 验收

所有档位都按 [布局几何门禁](layout-quality-gate.md) 生成结构化 `layout-geometry` 证据；优先在 build 后一次批量 read-back 中完成，不用逐节点截图增加往返。


- 角色、方向、双轴对齐、分布、子节点尺寸策略和视觉层级符合 Screen Spec；不能全部继承左上默认。
- 最终边界无泄出，中间容器未误裁；overflow 证据的 `escapes` 为空。
- 复用现网的区域逐元素对照过基线，超差项已修复或授权。
- 本次自建 layout-only 的 fills / strokes / effects 均为空，surface 有明确职责；结构读回与截图互相验证。
- 递归验证独立表面与实际承载背景、同层兄弟的层级；区分方式有职责依据，已有有效边界未被重复装饰。
- surface 或 overlay 内纯布局槽没有二次底色；独立子表面有职责与规范依据。
- 浮层高度 hug，除非 description 与场景同时要求分档或最大高度。
- 业务屏和模块根是 auto-layout Frame，不是 Group。
- 声明距未被外层再叠；无声明距的相邻块已按间距规范补距。
- 贴边壳层（顶栏、长按条、锁定操作条、键盘、Tab）已铺满画布，页面边距只包内容卡片/文本框，没有加在同时包含壳层的父级上。
- 圆角表单/列表旁的标题或底注（非 Markdown）已判断内收，文字对内边内容而不是外框。
- 正式实例保持自身约束和内部规范；description 要求处理的示意填充已从交付可见态去掉。
- 内容增长、主题、设备变化和 overlay 不破坏主任务；基线、文字框内对齐、换行与剩余空间已按适用项验证。
